# 32. 커밋·백업·롤백의 최소 습관

지금까지 명세서를 쓰고, 도구를 고르고, 작은 단위로 시키고, 오류를 고치는 법을 배웠다. 마지막으로 배울 것은 작업물을 안전하게 보관하는 습관이다. AI가 만들어준 결과물은 내 컴퓨터 어딘가에 파일로 있다. 컴퓨터가 고장 나거나, AI가 뭘 잘못 건드려서 파일이 망가지면 처음부터 다시 해야 한다. Git과 GitHub는 이럴 때 쓰는 도구지만, 이름부터 어렵게 느껴진다. 이 장에서는 터미널 명령 없이, GitHub 웹사이트의 클릭만으로 할 수 있는 최소 습관을 다룬다.

## Git·GitHub을 한 줄로 설명하면

Git은 "파일의 변경 이력을 저장하는 기능"이고, GitHub는 "그 이력을 인터넷에 보관하는 창고"다. 비개발자에게 필요한 것만 뽑으면 이렇다. 작업한 파일을 GitHub에 올려두면, 내 컴퓨터가 망가져도 인터넷에서 다시 받을 수 있고, 어제의 버전으로 되돌릴 수도 있다. 클라우드에 문서를 저장하는 것과 비슷하지만, "언제 무엇을 바꿨는지"가 날짜별로 남는다는 게 다르다.

## 가장 쉬운 백업법: GitHub 웹에서 5단계

처음 한 번만 저장소(파일을 담는 폴더)를 만들면, 이후에는 클릭 몇 번으로 백업이 끝난다.

### 1단계: GitHub에 가입하고 저장소를 만든다

github.com에 가입한다. 이메일 주소와 비밀번호로 가입할 수 있다. 로그인 후 오른쪽 위의 "+" 버튼을 눌러 "New repository"를 고른다. 저장소 이름은 프로젝트 이름으로 짓는다(예: afternoon-cafe-order). 이름은 영어로 짓는 게 나중에 편하다.

"Public"(공개)과 "Private"(비공개) 중 하나를 고른다. Public은 인터넷의 누구나 볼 수 있고, Private은 나만(또는 초대한 사람만) 볼 수 있다. 가게 메뉴판처럼 남이 봐도 되는 것이면 Public, 손님 정보나 내부 자료가 들어가면 Private을 고른다. 나중에 바꿀 수도 있다.

"Create repository"를 누르면 저장소가 만들어진다. 빈 폴더 하나가 인터넷에 생긴 것이다.

### 2단계: 파일을 업로드한다

저장소 화면에서 "uploading an existing file" 링크를 누른다(또는 "Add file" → "Upload files"). 백업할 파일들을 끌어다 놓는다. 폴더째로 올릴 수도 있다. AI가 만들어준 프로젝트 폴더를 통째로 올리면 된다.

파일이 많으면(수십 개 이상) 한 번에 올리기보다 폴더 단위로 나눠서 올린다. 업로드 중에 브라우저를 끄면 중단되니, 다 올라갈 때까지 기다린다.

### 3단계: 저장 메시지를 쓴다

파일 아래에 "Commit changes"라는 칸이 있다. 여기에 이번 저장에 대한 설명을 한 줄로 쓴다. 예: "메뉴판 화면 완성". 날짜는 자동으로 찍히므로 날짜를 굳이 쓸 필요는 없다. 이 메시지가 나중에 "언제 무엇을 했는지"를 알려주는 표지판이 된다.

처음 올릴 때는 "첫 업로드" 또는 "프로젝트 시작"이라고 적으면 된다.

### 4단계: "Commit changes" 버튼을 누른다

버튼을 누르면 업로드가 끝난다. "커밋"이라는 말이 어렵게 들리지만, 그냥 "지금 상태를 저장"하는 버튼이다. 여기까지가 백업 한 번이다.

### 5단계: 하루에 한 번 반복한다

작업한 날은 하루가 끝날 때 2~4단계를 반복한다. 바뀐 파일만 다시 올리면 된다. GitHub 웹에서는 같은 이름의 파일을 올리면 자동으로 덮어쓴다. 저장 메시지는 그날 한 일을 적는다. 예: "주문 확인 화면 추가", "품절 표시 수정".

작업 안 한 날은 저장할 필요가 없다. "하루에 한 번"은 "작업한 날은 그날 안에"라는 뜻이다.

## "하루에 한 번 저장" 규칙과 저장 메시지 쓰는 법

규칙은 단순하다. "작업한 날은 그날 안에 저장한다". 내일로 미루면 미룬 만큼 잃을 위험이 커진다. 5분이면 끝나니 일과를 마칠 때 습관처럼 한다.

저장 메시지는 다음 3가지 중 하나로 쓴다.

- 새로 만든 것: "메뉴판 화면 완성", "주문 완료 화면 추가"
- 고친 것: "품절 표시 수정", "픽업 시간 30분 단위로 변경"
- 되돌린 것: "주문 확인 화면을 어제 버전으로 복원"

메시지를 잘 쓰는 요령은 "무엇을"이 들어가게 쓰는 것이다. "수정함", "업데이트" 같은 말은 나중에 봐도 무슨 일을 했는지 모른다. "메뉴판 화면의 글자 크기 수정"처럼 대상이 드러나면 된다.

## 망가졌을 때 되돌리기

AI가 뭘 잘못 건드려서 화면이 깨졌다고 치자. 어제까지는 잘 됐는데 오늘 고장 났다. 이럴 때 쓰는 게 "이전 버전으로 되돌리기(롤백)"다.

### 순서 1: 히스토리에서 어제 버전을 찾는다

저장소 화면에서 "Commits"(또는 시계 모양 아이콘)를 누른다. 지금까지 저장한 목록이 날짜 순으로 나온다. 저장 메시지를 보고 "망가지기 전 마지막으로 잘 됐던" 저장을 찾는다. 저장 메시지를 잘 써둔 게 여기서 빛을 발한다. "수정함"만 적혀 있으면 어느 게 잘 되던 버전인지 알 수 없다.

### 순서 2: 이전 버전을 확인한다

목록에서 해당 저장을 누르면 그때의 파일들이 보인다. "Browse files"를 눌러 파일 내용을 확인할 수 있다. 정말 그 버전이 잘 되던 것인지 저장 메시지와 날짜로 판단한다.

### 순서 3: 파일을 복원한다

가장 쉬운 방법은 해당 버전의 파일을 다운로드받아서 내 컴퓨터의 파일과 교체하는 것이다. 파일 화면에서 파일명을 누르고, 오른쪽 위의 다운로드 아이콘을 누른다. 여러 파일이 망가졌다면, 그 버전 전체를 내려받아 폴더째 교체한다.

내려받은 파일로 교체하기 전에, 지금(망가진) 파일을 따로 백업해 둔다. 폴더 이름을 "망가진버전-보관"처럼 바꿔서 옆에 두면 된다. 복원한 버전도 마음에 안 들 경우를 대비한 보험이다.

### 되돌린 뒤에는 저장 메시지를 남긴다

복원이 끝나고 화면이 잘 뜨는 것을 확인했으면, 다시 2~4단계로 저장한다. 메시지는 "주문 확인 화면을 10월 15일 버전으로 복원"처럼 적는다. 나중에 "왜 이 버전이지?" 하고 헷갈리지 않게 된다.

## 실수로 비밀값을 올렸을 때의 대처

API 키(예: sk-test-dummy-1234 같은 형태)나 비밀번호를 실수로 GitHub에 올렸다면 이렇게 한다.

1. 일단 해당 파일을 GitHub에서 지운다. 파일 화면에서 휴지통(Delete) 아이콘을 누르고 저장 메시지를 적어 커밋한다. 메시지는 "비밀값이 포함된 파일 삭제"처럼 적는다.
2. 하지만 이것만으로는 부족하다. 지우기 전의 이력에 비밀값이 남아 있기 때문이다. 이력이 Public 저장소에 있었다면, 그 키는 이미 노출된 것으로 보고 해당 서비스에서 키를 새로 발급(재발급)받는다. 재발급 방법은 각 서비스의 설정 화면에 있다.
3. 앞으로는 비밀값이 들어간 파일을 올리기 전에 확인한다. AI에게 "이 프로젝트에 비밀값(API 키, 비밀번호)이 들어간 파일이 있냐"고 물어보면 찾아준다.

가장 좋은 예방법은 비밀값을 코드 파일에 직접 적지 않는 것이다. AI에게 "비밀번호는 코드에 직접 적지 말고 별도 설정에서 읽게 해줘"라고 말하면 된다. 그래도 실수는 생기니 위 대처법을 알아둔다.

## 자주 묻는 질문

### Public으로 올려도 내 컴퓨터의 다른 파일이 공개되나요?

아니다. 올린 파일만 공개된다. 저장소에 올리지 않은 파일은 내 컴퓨터에만 있다. 그래서 "올릴 파일을 고르는 것"이 중요하다. 프로젝트 폴더만 올리고, 개인정보가 든 파일은 올리지 않는다.

### 파일을 올렸는데 화면이 이상해졌어요

업로드 자체는 파일을 복사하는 것이라 화면을 망가뜨리지 않는다. 화면이 이상해졌다면 업로드와 별개의 문제다. 31장의 디버깅 대화법으로 AI에게 물어본다.

### 저장 메시지를 잘못 썼어요. 고칠 수 있나요?

웹에서는 저장 메시지를 직접 고치기 어렵다. 그냥 다음 저장 때 제대로 적으면 된다. 메시지 하나 틀렸다고 큰일은 안 난다.

### 컴퓨터를 바꿨는데 파일을 어떻게 가져오나요?

새 컴퓨터에서 GitHub 저장소 화면에 들어가 "Code" 버튼을 누르고 "Download ZIP"을 고른다. 압축을 풀면 파일이 그대로 있다. 이어서 작업하면 된다.

## 최소 습관 정리

이 장의 내용을 한 장으로 줄이면 다음과 같다.

- 작업한 날은 하루가 끝날 때 GitHub에 저장한다(5단계).
- 저장 메시지에는 "무엇을" 했는지 적는다.
- 망가졌으면 히스토리에서 잘 되던 버전을 찾아 파일을 교체한다.
- 비밀값을 올렸으면 파일을 지우고 키를 재발급받는다.

이 4가지만 지키면 "처음부터 다시" 하는 일은 거의 없어진다. 백업은 지루하지만, 한 번 구해주면 그 가치를 알게 된다. Part 3은 여기서 끝난다.

## 백업이 실제로 구해준 사례

"오후의 쉼표" 사장님이 30장의 6단계로 주문 앱을 만들었다고 치자. 4단계(주문 확인 화면)까지 잘 됐는데, 5단계에서 AI가 파일을 잘못 건드려 메뉴판 화면까지 깨졌다. 미리보기가 하얗게 나왔다.

사장님은 당황하지 않고 GitHub 저장소의 Commits를 열었다. 저장 메시지를 보니 "주문 확인 화면 추가"가 마지막으로 잘 되던 버전이었다. 그 버전의 파일들을 내려받아 교체했더니 메뉴판 화면이 돌아왔다. 5단계는 처음부터 다시 했지만, 1~4단계는 건드리지 않아도 됐다. 걸린 시간은 30분이었다.

백업이 없었다면 1~4단계를 다시 설명하고 만드는 데 하루가 걸렸을 것이다. "하루에 한 번 저장" 5분이 하루를 벌어준 셈이다.

## 협업할 때의 최소 규칙

나중에 다른 사람(예: 도와주는 지인, 외주 개발자)과 함께 작업하게 되면 저장소 공유가 필요해진다. 이때의 최소 규칙 2가지다.

1. 저장소는 Private으로 유지한다. 손님 정보나 가게 내부 자료가 들어갈 수 있기 때문이다.
2. 함께 작업하는 사람을 저장소의 "Collaborator"로 초대한다. 저장소 화면의 Settings → Collaborators에서 이메일로 초대할 수 있다.

서로 다른 사람이 같은 파일을 동시에 고치면 충돌이 날 수 있다. 그럴 때는 "누가 어느 파일을 맡는지"를 미리 정해둔다. 예: "사장님은 메뉴 데이터, 지인은 화면 디자인".

## 터미널 명령을 써보고 싶어지면

이 장에서는 웹 클릭만으로 끝냈지만, 나중에 터미널 명령에 도전하고 싶어질 수 있다. 그때 알아둘 최소 명령 3개다.

```
git add .
git commit -m "메뉴판 화면 완성"
git push
```

위 3줄이 이 장의 2~4단계와 같은 일이다. 파일을 모으고(add), 저장 메시지를 적고(commit), GitHub에 올린다(push). AI에게 "이 폴더를 GitHub에 올리는 명령을 알려줘"라고 물으면 상황에 맞게 알려준다. 억지로 외울 필요는 없고, 웹 방식이 편하면 계속 웹으로 해도 된다.

## 이 책의 순서 되돌아보기

Part 2와 Part 3에서 배운 것을 순서대로 정리하면 다음과 같다.

1. 명세서를 쓴다(20장). 목적·사용자·화면·데이터·예외를 한 장에 정리한다.
2. 템플릿에 옮긴다(21장). 화면 흐름도·데이터 항목표·예외 상황표를 채운다.
3. 도구를 고른다(22장). 무료로 시작해 필요하면 유료 1개를 고른다.
4. 작은 단위로 시킨다(30장). 한 요청에 한 화면, 각 단계 후 눈으로 확인한다.
5. 안 되면 고치게 한다(31장). 증상 4요소로 설명하고, 3번 반복되면 멈춘다.
6. 매일 백업한다(32장). 작업한 날은 그날 안에 GitHub에 저장한다.

이 6단계를 한 바퀴 돌리면 작은 프로젝트 하나가 완성된다. 두 바퀴째부터는 속도가 붙는다.
