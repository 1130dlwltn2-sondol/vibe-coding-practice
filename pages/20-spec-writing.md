# 20. AI가 이해하는 명세서 쓰기

AI 코딩 도구에 원하는 것을 말했는데, 결과물이 생각과 전혀 다르게 나온 경험이 있다. 보통은 AI가 멍청해서가 아니라 지시가 모호해서다. 사람은 대충 말해도 눈치로 알아듣지만, AI는 말한 그대로만 이해한다. 그래서 AI에게 일을 시키기 전에 '명세서'라는 정리된 문서가 필요하다.

명세서는 어렵게 들리지만 사실은 'AI에게 주는 일거리 목록'이다. 개발자만 쓰는 전문 문서가 아니다. 카페 사장님이 인테리어 업자에게 도면을 주듯이, AI에게 만들 것을 그림과 목록으로 정리해 주는 것이다. 이 장에서는 AI가 명세서를 못 알아듣는 흔한 이유 3가지를 먼저 보고, 좋은 명세서의 5가지 요소, 그리고 비개발자도 30분 안에 쓸 수 있는 작성 순서를 다룬다.

## AI가 명세서를 못 알아듣는 흔한 이유 3가지

### 1. 모호한 지시

"예쁜 홈페이지 만들어줘"처럼 들으면 사람도 감이 안 잡히는 말이 가장 흔한 문제다. 예쁘다는 게 무슨 색인지, 홈페이지가 무엇을 파는 건지, 누가 보는 건지 정보가 없다. AI는 이런 빈칸을 자기 나름대로 채워서 만든다. 그 결과는 십중팔구 원하는 것과 다르다.

"예쁜" 대신 "흰 배경에 검은 글씨, 메뉴판은 가운데 크게"라고 하면 달라진다. AI에게 주는 말은 '느낌'이 아니라 '구체적인 모양'이어야 한다. 이 장 후반의 나쁜 예 vs 좋은 예에서 직접 비교해 보겠다.

### 2. 누락된 예외

명세서에 '정상적인 경우'만 적고 '이상한 경우'를 빠뜨리는 실수다. 예를 들어 주문 앱 명세서에 "손님이 메뉴를 고르고 주문한다"까지만 쓰고, "품절된 메뉴를 골랐을 때 어떻게 하냐"를 안 적는 것이다. AI는 안 적힌 부분은 아예 구현하지 않거나, 알아서 대충 만든다.

나중에 "품절 처리가 안 돼요"라고 말하면 되지만, 처음부터 적어두면 두 번 일하지 않아도 된다. 예외 상황은 21장에서 표 템플릿으로 따로 정리하는 방법을 다룬다.

### 3. 화면과 데이터의 불일치

"회원 가입 화면을 만들어줘. 이름과 이메일을 받는다"고 써놓고, 정작 명세서의 데이터 항목에는 '전화번호'도 들어가 있는 경우다. 화면에서 입력받는 항목과 데이터로 저장해야 하는 항목이 어긋나면 AI가 헷갈린다. 저장할 곳이 없는데 화면에서 받으라고 하거나, 화면에는 없는데 저장하라고 하거나 둘 중 하나가 생긴다.

화면에 그려지는 입력 칸과 뒤에서 저장되는 데이터를 한 문서 안에서 나란히 적어두면 이 불일치를 미리 발견할 수 있다.

## 좋은 명세서의 5요소

좋은 명세서에는 항상 다음 5가지가 들어 있다. 5가지를 다 채우면 AI가 결과물을 만들어낼 때 헤매는 구간이 확 줄어든다.

### 요소 1: 목적 — 왜 만드는가

이 앱(사이트)이 존재하는 이유를 한두 문장으로 적는다. "카페 홍보용 홈페이지"와 "카페 온라인 주문 앱"은 완전히 다른 결과물이 나온다. 목적이 정해지면 AI가 화면 구성이나 기능을 판단할 때 기준이 생긴다.

예: "우리 카페의 메뉴를 보여주고, 매장 픽업 주문을 받기 위한 모바일 웹페이지"

### 요소 2: 사용자 — 누가 쓰는가

사용자가 누구인지 적는다. 연령대나 이용 환경을 적으면 AI가 글자 크기, 버튼 크기, 복잡도를 알아서 조절한다. "50대 이상 손님도 쉽게"라는 한 줄이 들어가면 버튼이 커지고 절차가 단순해진다.

예: "20~40대 카페 손님. 스마트폰으로 접속. 매장 앞에서 주문하는 경우가 많음"

### 요소 3: 화면 목록 — 어떤 화면이 있는가

앱에 들어가는 화면을 전부 나열한다. 화면마다 이름과 역할을 한 줄씩 적는다. 화면이 3개인지 10개인지가 정해지면 AI가 작업량을 파악하고, 화면끼리 어떻게 연결되는지도 정할 수 있다.

예:
- 첫 화면: 메뉴판 목록 (음료·디저트 카테고리 탭)
- 주문 화면: 선택한 메뉴 확인, 수량 조절, 픽업 시간 선택
- 완료 화면: 주문 번호 표시, "준비되면 알려드립니다" 안내

### 요소 4: 데이터 항목 — 무엇을 저장하는가

화면에서 입력받거나 저장해야 하는 정보를 목록으로 적는다. 항목마다 이름, 형식(글자·숫자·날짜 등), 필수 여부를 적는다. 21장에서 이 부분을 표 템플릿으로 정리하는 방법을 다룬다.

예: 주문 데이터 — 메뉴명(글자, 필수), 수량(숫자, 필수), 픽업 시간(시간, 필수), 요청 사항(글자, 선택)

### 요소 5: 예외 상황 — 이상할 때 어떻게 하는가

"이러면 어떻게 해?"에 대한 답을 미리 적는다. 전부 적을 필요는 없고, 자주 일어날 것 같은 것 3~5개만 적어도 충분하다.

예:
- 품절 메뉴를 선택하면: "품절입니다" 표시, 주문 버튼 비활성화
- 픽업 시간을 과거 시간으로 고르면: 다시 선택하라는 안내 표시

## 나쁜 예 vs 좋은 예

같은 기능(카페 메뉴판 사이트)을 두 가지 방식으로 지시했을 때를 비교해 보자.

### 나쁜 예

```
예쁜 카페 홈페이지 만들어줘.
메뉴도 보여주고 주문도 되게 해줘.
```

이 지시의 문제점을 5요소로 점검하면 이렇다. 목적은 '홍보용인지 주문용인지' 불분명하고, 사용자는 누구인지 없고, 화면이 몇 개인지 모르고, 주문할 때 어떤 정보를 받는지 없고, 예외는 당연히 없다. AI는 전부 자기 마음대로 채워서 만든다. 색도 마음대로, 메뉴 구성도 마음대로, 주문 절차도 마음대로다. 결과물을 보고 "이게 아닌데"를 반복하게 된다.

### 좋은 예

```
[목적]
우리 카페(가게명: 오후의 쉼표)의 메뉴를 보여주고
매장 픽업 주문을 받는 모바일 웹페이지

[사용자]
20~40대 손님. 스마트폰으로 접속.
매장 앞에서 주문하는 경우가 많으므로 버튼은 크게.

[화면 목록]
1. 메뉴판 화면: 음료/디저트 탭으로 메뉴 목록 표시.
   각 메뉴에 이름·가격·사진·품절 표시.
2. 주문 화면: 담은 메뉴 목록, 수량 조절(+/- 버튼),
   픽업 시간 선택(10분 단위), 요청 사항 입력 칸.
3. 완료 화면: 주문 번호 크게 표시.
   "준비되면 문자로 알려드립니다" 안내.

[데이터 항목]
- 메뉴명(글자, 필수), 가격(숫자, 필수)
- 수량(숫자, 필수), 픽업 시간(시간, 필수)
- 요청 사항(글자, 선택)

[예외 상황]
- 품절 메뉴 선택 시: "품절입니다" 표시, 담기 버튼 비활성화
- 픽업 시간을 현재보다 이른 시간으로 고르면:
  "현재 시간 이후로 선택해 주세요" 안내 표시
```

같은 카페 메뉴판 사이트인데, 들어가는 정보량이 완전히 다르다. 좋은 예에는 AI가 마음대로 정할 여지가 거의 없다. 색상까지는 안 적었지만, 사용자가 "매장 앞에서 쓰는 손님"이라는 정보에서 AI가 버튼 크기와 단순한 구조를 유도할 수 있다.

## 비개발자도 30분 안에 쓰는 명세서 작성 순서

명세서는 처음부터 완벽하게 쓸 필요가 없다. 아래 순서대로 30분만 투자하면 AI에게 바로 건넬 수 있는 수준이 된다.

### 1단계 (5분): 한 문장으로 목적 정하기

"누가, 무엇을 하기 위한 것인가"를 한 문장으로 쓴다. 예: "단골 손님이 매장 픽업 주문을 하기 위한 모바일 페이지". 이 한 문장이 전체 명세서의 기준이 된다. 흔들리면 이 문장으로 돌아온다.

### 2단계 (5분): 화면을 손으로 그리기

종이나 메모 앱에 화면을 네모로 그리고 안에 들어갈 것을 글자로 적는다. 잘 그릴 필요가 없다. 화면이 몇 개인지, 각 화면에 뭐가 들어가는지만 보이면 된다. 이 스케치가 화면 목록의 재료가 된다.

### 3단계 (10분): 5요소 채우기

위의 좋은 예 형식을 그대로 복사해서 5요소를 채운다. 목적과 사용자는 1단계 문장에서 가져오고, 화면 목록은 2단계 스케치에서 가져온다. 데이터 항목은 각 화면의 입력 칸을 보며 적고, 예외 상황은 "손님이 이상하게 쓰면?"을 3개만 떠올려 적는다.

### 4단계 (10분): AI에게 검토받기

작성한 명세서를 AI에게 그대로 붙여넣고 이렇게 물어본다.

```
이 명세서를 보고 만들려고 하는데,
빠진 부분이나 모호한 부분이 있으면 질문해줘.
```

AI가 질문하는 부분 = 명세서의 빈틈이다. 그 질문에 답해서 명세서에 추가하면 된다. 이 과정을 거치면 명세서의 완성도가 한 단계 올라간다.

이 4단계를 거친 명세서는 21장의 템플릿에 그대로 옮겨 담을 수 있다. 다음 장에서는 화면 흐름도, 데이터 항목표, 예외 상황표를 복사해서 바로 쓰는 형태로 제공한다.

## 명세서와 프롬프트는 다르다

"명세서를 쓰라는 게 결국 프롬프트 잘 쓰라는 말 아니냐"고 물을 수 있다. 비슷하지만 역할이 다르다. 프롬프트는 AI에게 그때그때 시키는 말이고, 명세서는 프로젝트 전체를 정리한 기준 문서다. 프롬프트는 매번 바뀌지만 명세서는 프로젝트가 끝날 때까지 곁에 둔다.

구체적으로 이렇게 쓴다. 명세서는 파일 하나(메모장, 구글 독스, 노션 어디든)로 만들어 둔다. AI에게 일을 시킬 때마다 명세서 전문을 앞에 붙이고, 그날 할 일을 뒤에 붙인다.

```
[명세서 전문 붙여넣기]

오늘 할 일: 메뉴판 화면만 만들어줘.
```

이렇게 하면 AI는 매번 전체 그림을 보면서 부분 작업을 한다. 명세서 없이 "메뉴판 화면 만들어줘"만 반복하면, 나중에 만든 화면과 먼저 만든 화면의 디자인이 따로 놀게 된다.

## 자주 하는 실수 3가지와 고치는 법

### 실수 1: "알아서 해줘"를 남발한다

"디자인은 알아서 예쁘게 해줘" 같은 말은 AI에게 전권을 넘기는 것과 같다. AI는 예쁘게 만들려고 노력하지만, 그 예쁨이 내 가게 분위기와 맞을 보장은 없다. 색상, 분위기(깔끔한/따뜻한/고급스러운), 참고할 만한 사이트 정도는 직접 정해주는 게 낫다.

고치는 법: "흰색 바탕에 갈색 포인트, 우리 가게 간판 같은 따뜻한 느낌"처럼 기준이 되는 말을 넣어준다.

### 실수 2: 기능을 나열만 하고 순서를 안 적는다

"주문도 되고, 메뉴 관리도 되고, 매출 확인도 되게 해줘"라고 하면 AI는 3개를 어떻게 연결해야 할지 모른다. 손님이 주문하면 사장님 화면에 어떻게 뜨는지, 매출은 어디서 모이는지 순서가 빠져 있다.

고치는 법: 화면 흐름도(21장)에 "주문 완료 → 사장님 화면의 새 주문 목록에 표시"처럼 연결을 적는다.

### 실수 3: 한 번에 다 고치려 한다

명세서를 AI에게 주고 결과물이 나왔는데 마음에 안 들면, 명세서 전체를 뜯어고치고 싶어진다. 하지만 한 번에 여러 곳을 고치면 뭐가 문제였는지 알 수 없다. 30장에서 다루겠지만, 수정도 작은 단위로 하는 게 원칙이다.

고치는 법: "메뉴판 화면의 메뉴 이름 글자를 더 크게 해줘"처럼 한 화면의 한 요소만 지정해서 고친다.

## 실제 사례: 명세서 유무에 따른 차이

같은 사람이 같은 카페 메뉴판 사이트를 두 번 만들었다고 가정해 보자. 첫 번째는 "예쁜 카페 홈페이지 만들어줘" 한 줄로 시켰다. AI는 파란색 계열의 세련된 디자인을 만들었다. 그런데 이 카페는 원목 인테리어의 따뜻한 분위기라 어울리지 않았다. 메뉴는 20개인데 화면에는 6개만 예시로 들어갔고, 주문 기능은 없었다. 다시 설명하고 고치는 데만 3일이 걸렸다.

두 번째는 이 장의 4단계로 명세서를 먼저 썼다. "흰 바탕에 갈색 포인트, 따뜻한 느낌"이라고 적었고, 화면 3개와 데이터 항목, 예외 4개를 정리했다. AI가 만든 첫 결과물은 색상부터 화면 구성까지 명세서대로 나왔다. 고친 것은 픽업 시간 간격(10분→30분) 하나뿐이었다. 걸린 시간은 반나절이었다.

차이는 AI의 실력이 아니라 준비였다. 명세서는 AI를 위한 문서이면서, 동시에 내 생각을 정리하는 도구다. 명세서를 쓰는 30분은 나중에 고치는 3일을 아껴준다.
